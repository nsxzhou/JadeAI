## 1. 背景与目标

产品里存在两个面试功能：

- `/interview` — **模拟面试**：AI 扮演面试官与求职者多轮对话，产出提升报告。
- `/recruit` — **招聘侧**：面试官建岗位、传候选人简历、AI 出题、边问边记、AI 评价。

前者工程质量低（管线漏数据、无测试），后者工程质量高（蓝图校验、服务端算分、全量单测）但**没有任何用户**——它是给招聘方用的，而本产品的主业是求职者。

本次重构做三件事：

1. **把两个功能统一为同一个领域概念的两个实例**，抽出共享内核，让高质量的那套逻辑成为两个实例的共同地基。
2. **把 `/recruit` 翻转为「面试官视角」**——求职者用它推演"我会被怎么问、会被怎么判"。
3. **在候选侧补上三样它现在没有的东西**：可信的管线、真实的约束、可累积的资产。

### 非目标（本次明确不做）

- **语音**（ASR/TTS）：本期不做，但内核接口预留（见 7.6）。
- **切屏检测 / 禁止查资料**：明确不做（理由见 7.3）。
- **题目跨场次复用**：明确不做——C 端样本量撑不起题库价值（见 7.4）。
- **RAG / 向量检索**：明确不做。
- **多租户 / 团队协作 / 权限体系**：产品立场仍是"单用户、本地数据、BYOK"，不转 B 端。
- **投递 / 职位发布 / 双端撮合**：面试官视角是"自我推演"，不是招聘流程。

## 2. 产品立场（核心转向）

**使用者是求职者。** 由此推导出本次最重要的一次语义翻转：

| | 改造前 | 改造后 |
|---|---|---|
| `/recruit` 的使用者 | 招聘方（HR / 面试官） | **求职者本人** |
| 「岗位」的含义 | 我要招的岗位 | **我的目标岗位** |
| 「候选人」的含义 | 别人（被评估的人） | **我自己**（我要被怎么评估） |
| 这个功能的用途 | 辅助招聘决策 | **推演我会被怎么问、会被怎么判** |

翻转的**理由**不是"别浪费代码"，而是：`/recruit` 那套产物（出题依据、考察意图、三档评分标准、危险信号）**恰好是求职者花钱都买不到的信息**。模拟面试里"AI 临场想一道题"永远给不了"这道题面试官到底在看你什么、什么答案会被判不合格"。

因此产品里不再有"招聘"，只有**同一场面试的两种玩法**：

- **模拟面试** — 面试官由 AI 扮演，目的是练习。
- **面试官视角** — 面试官由"假设的真人"扮演，目的是预判。

两者共享同一个入口（`/interview`），用户在同一个地方切换。命名裁决见 `GLOSSARY.md`：**「招聘」是应避免的叫法**。

## 3. 领域模型与共享内核

承认一件事：两个功能是同一个概念的两个实例。

```
面试 = 面试官 × 候选人 × 题目集 × 逐题回答 × 评分
```

区别只有两处：**谁扮演面试官**（AI / 假设的真人），**目的是什么**（练习 / 预判）。

### 3.1 共享什么，不共享什么

**共享：名词 + 纯函数。**

- `InterviewQuestion` / `DimensionConfig` / `DimensionScore` / `InterviewBlueprint` 的**单一定义**
- 出题：岗位族 → 蓝图 → 逐槽位生成 → 校验
- 评分：维度分 → 服务端加权算分
- `evidence` 的来源归类与归一化校验
- 能力画像的累积、错题本的判定

**不共享：交互形态。**

候选人侧是**对话式**（流式、自适应追问、即时反馈），面试官视角是**文档式**（出题 → 逐题记录 → 评价）。这个差异是真实的，不该被抹平——招聘侧原设计文档已经论证过强行合并的代价（空字段 + 组件长满 if 分支）。

共享的边界停在**名词和纯函数**，不越过交互。

### 3.2 内核位置

新建 `src/lib/interview-core/`：

| 文件 | 职责 |
|---|---|
| `types.ts` | `InterviewQuestion` / `DimensionConfig` / `DimensionScore` / `InterviewBlueprint` / `QuestionSlot` 的唯一定义（含 zod schema） |
| `dimension.ts` | 维度配置校验、`allocateQuestions`（按评分权重分配题数） |
| `role-family.ts` | 岗位族清单、每族的必考主题与题型配比 |
| `blueprint.ts` | 蓝图生成编排 + `validateBlueprint`（自 `src/lib/ai/recruit-blueprint.ts` 抽出并泛化） |
| `evidence.ts` | `evidence` 的 Unicode/大小写/空白归一化与精确成员校验 |
| `scoring.ts` | `computeOverallScore` 等加权算分（自 `src/lib/recruit/scoring.ts` 抽出） |
| `profile.ts` | 能力画像的累积与坐标映射 |
| `weak-questions.ts` | 错题本判定（服务端阈值） |

`src/types/interview.ts` 与 `src/types/recruit.ts` 改为从 `interview-core/types.ts` 再导出，避免两套定义并存。

### 3.3 一个必须先修的模型缺陷

`DimensionConfig.weight` 现在承载**两个含义**（`job-form-dialog.tsx:61`）：

| 场景 | `weight` 实际含义 |
|---|---|
| 评分 | 相对权重，用于加权平均 |
| 出题 | 这个维度分配几道题 |

两者寿命不同：**评分口径长期稳定**（画像可比的前提），**出题数量是每场策略**。必须拆成两个字段：

```
DimensionConfig {
  key, label, custom,
  weight: number,          // 评分口径，岗位配置时定，长期不变
}
InterviewConfig {
  questionCount: number,   // 本场出题数，可按场调整
}
```

候选人侧**不向用户暴露逐维度题数**（你没法选"我被考几道抗压题"），只给粗粒度预设：**短 6 / 标准 10 / 长 15**。面试官视角保留 5–20 逐维度可调——真人面试官确实需要这个控制权。

## 5. 需要你确认的一处延伸

以下这一点**超出了对你答案的字面解读**，是我为了满足 Q6 而必须做的推论，请你确认或否决：

> **两个模式的题目应该落进同一张 `interview_questions` 表，而不是一个进表、一个留在 JSON 里。**

理由：

1. Q6 要求"题目"只有一份定义。若候选人侧落表、面试官视角留在 `recruit_candidates.questions` JSON（`schema-recruit.ts:25`），则仍是两套存储。
2. Q8 的错题本要求题目**可跨场次查询**，JSON 列做不到。
3. 面试官视角原设计把题目放 JSON 的理由是"一人一套、无跨候选人复用"——但该理由对两个模式同样成立，不足以支撑两套存储。

代价：一次数据迁移（`recruit_candidates.questions` JSON → 行）。

如果你否决，替代方案是候选人侧落表、面试官视角维持 JSON，代价是两套读写路径。

## 7. 分模块设计

### 7.1 管线可信（Q9）

现在候选侧的缺陷全部是"用户能看见的错"：

| 症状 | 位置 | 处理 |
|---|---|---|
| 标记/提示/跳过从未落库 | `control-bar.tsx:38-47` 只写 Zustand；`chat/route.ts:79-83` 用新 UUID 存消息，与前端 id 不匹配 | 改为服务端生成 id 后回传、前端以此为准；控制指令直接写 `interview_messages.metadata` |
| 轮次小结分数硬编码为 0 | `chat/route.ts:89-92` | 删除该字段的写入；轮次分改由服务端按该轮题目分数聚合 |
| 列表卡片分数永远空白 | `interview-card.tsx:62-64`；`findSessionsByUserId` 未 join 报告 | 列表查询补上报告摘要 |
| `maxQuestions` 服务端无上限 | 仅存在于 prompt（`interview-prompts.ts:47,109`） | 服务端硬性截断，达到上限强制收轮 |
| 报告单次非流式、无重试、失败静默 | `report/route.ts:147-164` | 改为**逐轮生成 + 全场汇总**（见下）；失败可重试且不吞错误 |
| Zod schema 全字段 `.default()`，形状错但合法会静默产出 0 分空报告 | `interview-report-schema.ts` | 改为强约束，关键字段缺失即报错 |
| `InterviewerConfig.systemPrompt` 死字段 | `interviewers.ts` 所有预设均为 `''` | 删除 |
| 进度 off-by-one（`0/N 轮`） | `interview-card.tsx:59-60,92` | 修正显示 |
| 面试官拖拽排序未实现 | `interviewer-picker.tsx:25-32` | 用 `@dnd-kit` 实现（仓库已依赖） |
| 全模块仅 31 行测试 | `round-status.test.ts` | 补纯函数与路由测试 |

**报告生成改为两段式**（解决长面试截断）：

1. 每轮结束即生成该轮的评估（输入只有本轮对话），落库。
2. 全场结束时生成汇总（输入是各轮评估，**不重读全文**）。

这同时天然支持"逐轮出报告"，并让单次请求的 token 量可控。

**报告生成触发点**从"访问报告页时生成"改为"结束面试时生成（带进度）"，失败可重试且明确提示，不再表现成"加载失败"。

### 7.2 出题：蓝图 + 事实来源 + 岗位族（Q10 / Q14 / Q17 / Q18）

**蓝图照搬招聘侧（已被验证）**：先规划整场题型与知识覆盖（`resumeFacts` / `jdRequirements` / `gaps` / `slots`），再按维度并发逐槽位生成；服务端硬校验槽位数、维度配额、`evidence` 精确匹配；失败整次不落库，不覆盖旧题。

**分工**：蓝图决定**问什么**，对话决定**怎么问、追问多深**。既有自适应追问保留——但中途换方向必须走显式的"跳过并换题"，不再由模型自行决定。

**事实来源三分类**（`source`）：

- `resume` — 只引用简历明确写出的项目、职责、技术和数字
- `jd` — 基于 JD 的假设场景，题干必须明确是场景，不得暗示候选人做过
- `gap` — JD 要求但简历未证明的能力，不得伪装成项目经历

**JD 定范围，简历定取证**：范围来自目标岗位（真实面试考的是岗位要什么），个性化来自简历。

**岗位族替代 `detectGoRole`**：`recruit-blueprint.ts:12-31` 的硬编码正则换成 `role-family.ts` 的**静态清单 + LLM 选择**，清单含"其他"兜底。每族自带必考主题、题型配比、评分风格。纯 LLM 自由判定被否决——判定漂移会污染画像坐标。

**面试官摘掉维度所有权**：面试官仍保留 6 种预设（HR 面 / 技术面 / 场景面 / 行为面 / 项目深挖 / Leader 面），它决定**提问侧重与风格**；评分坐标统一由 7.4 的两层坐标系给出。面试官不再提供 `focusAreas` 作为评分维度。

### 7.3 真实约束（Q7 / Q12 / Q20）

| 约束 | 设计 |
|---|---|
| **限时** | 每题倒计时，默认 3 分钟；整场限时 = 题数 × 3 分钟 × 1.1 |
| **超时行为** | **保存已写内容**，自动进入下一题，报告中标注该题超时。绝不丢答案——丢答案会让人不敢开口，反而削弱练习价值 |
| **不可回改** | 提交即定；不得编辑历史回答 |
| **暂停** | 保留按钮，但**计时不停**（像真实面试里走神）。这让"中断"失去换取思考时间的价值，同时保住技术上的可恢复 |
| **压力面** | **默认温和**：不放过模糊表述——出现"大概 / 差不多 / 我们团队"时抓住不放，逼出确切数字与**个人**贡献。强度可选（温和 / 标准 / 尖锐）。**不做尖锐羞辱式** |
| **反问环节** | 面试最后一题由候选人向面试官提问，AI 评价提问质量 |
| **多轮串联** | 多面试官已按顺序串联，补上轮次之间的状态与间隔 |
| **切屏检测** | **不做**。浏览器失焦不等于作弊，技术上不可靠；且把用户当嫌疑人与"练习"定位冲突——**练习场不该有监考** |

### 7.4 资产：能力画像 + 错题本（Q8 / Q15 / Q21）

**两层坐标系**（这是画像成立的前提）：

- **通用层** — 所有面试都测：沟通表达、逻辑思维、抗压能力、学习能力
- **岗位族层** — 由 `roleFamilyKey` 决定，如后端的 Go 并发、数据库、中间件

现状的问题正是坐标不固定：6 种面试官各有独有维度，导致**两次面试的分数不可比**。两层坐标让两句话同时成立：

- "我这三个月**沟通表达**涨了 12 分"（通用层，跨岗位族可比）
- "我的 **Go 并发**还是弱"（族层，进错题本）

**错题本判定**：**服务端**对单题分数应用绝对阈值（**< 60**）判定，外加用户手动标记。

- **不用相对阈值**——它会跟着你一起退步：整体水平下降时阈值同步下降，该收的题反而收不进，而错题本的全部意义就是"在你还没意识到自己差的时候指出来"。
- **不用纯 AI 判定**——同一模型两次跑对同一份回答的"薄弱"判断会漂。

配套：错题**跨场次保留题干与考察意图**；**重练 = 生成一场只含错题的短面试**（上限 10 题），答完并排展示前后两次回答。

现有的 `history-comparison` 组件并入能力画像，不再单独存在。

### 7.5 面试官视角模式（Q5 / Q16 / Q19）

- **入口**：`/interview` 大厅增加模式切换，两个模式同一个入口。
- **路由**：`/interview/perspective/*`。⚠️ 注意它与 `/interview/[id]` 在同层存在静态段与动态段——Next.js 中静态段优先，但会与短 id 存在理论碰撞。实现时需加保留字守卫（或改用不与 id 冲突的段名）。
- **数据**：复用第 6.4 节重命名后的三张表。
- **交互**：保留现有文档式形态——面试台全屏、逐题边问边记、防抖落库、键盘切题。**这些是已被验证的形态，不改。**
- **新增**：出题改用共享内核（岗位族 + 蓝图 + 两层坐标）。

### 7.5.1 落地结论（阶段 9 收尾）

`/interview/perspective` 的坐标与候选人侧完全一致：岗位族 + 语言栈定族层维度，
`question_counts` 定每维题数，`weight` 只表评分权重。三处细节由实现计划锁定：

1. **旧维度归位**——`communication_pressure → general_stress`、
   `hr_motivation → general_communication`，题型（`category`）保留不动。这正是
   「题型与评分坐标解耦」的用途：问一道求职动机题，分数落在沟通表达坐标上。
   通用层仍保持 4 维，不为「动机」新增坐标（坐标沉淀后不可改）。
2. **自定义维度**保留，归入族层、权重 2，只参与本场评分与报告，**不进能力画像**
   （key 不在目录里，`buildProfile` 自动排除）。
3. **画像与错题本合并两个来源**：两种玩法共用坐标，画在同一条线上，每个点带
   `source: mock | perspective`；错题本同理，重练一律新建一场模拟面试。

### 7.6 语音（本期不做）

范围与技术的结论已定，留待后续实施：

- **只做语音输入**（你说，AI 听），不做 AI 语音提问（TTS）。
- 技术先用浏览器 `Web Speech API`，把 `SpeechToText` 抽成接口，日后可换 Whisper / 讯飞。
- 本产品是 BYOK 模式，**多要一个 STT key 会明显抬高门槛**，先用免费方案验证需求。
- **必须处理的边界**：ASR 一定会把 "Goroutine"、"MVCC" 这类词听错。裁决——**修正 ASR 的转写错误不违反"不可回改"；修改自己的回答违反。** 界面必须让这两件事可区分（提交前的转写编辑被记录为"转写修正"，而非"答案修改"）。

### 7.7 顺带清理

- 清理遗留 i18n key（`prep` / `tabs` / `steps` 与旧维度名，`messages/zh.json:1012-1036`）。

## 10. 验收

**每个阶段的通用门槛**

- `pnpm test` 全绿，`tsc --noEmit` 干净
- 招聘/面试相关文件**不新增非 `any` lint 违规**（基线是 1340 个问题，几乎全是 `no-explicit-any`，验收标准是"不新增"）
- 中英两套 `messages` 键路径一致

**阶段专属**

- 阶段 1：连续记录三道题的答案与控制标记，刷新后全部还在；列表卡片显示上次总分
- 阶段 4：**报告里每一个数字都能追溯到一条原始消息**——这是"可信"的定义
- 阶段 5：人工检查一份 Go 岗 JD + 简历，蓝图必须覆盖语言基础 / 数据库中间件 / 项目深挖 / 系统场景 / 沟通压力，且**不得出现简历未证明的实现事实**
- 阶段 6：一道题超时后，已写内容仍在，报告中标注超时；历史回答无法编辑
- 阶段 7：连做三场面试，通用层维度分数可累积成趋势
